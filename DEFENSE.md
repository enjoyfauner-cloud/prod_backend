# Защита: backend «Советник»

## 1. Архитектура за 30 секунд

```
Frontend ──HTTP/JSON──▶ FastAPI ─┬─ api/        валидация (Pydantic), единый формат ошибок
                                 ├─ services/
                                 │   ├─ calculator.py  ЧИСТАЯ функция: карты + сумма + дата → результат
                                 │   ├─ repository.py  SQL (1 запрос на расчёт)
                                 │   └─ catalog_import.py  идемпотентный upsert справочника
                                 └─ observability/ JSON-логи с request_id, Prometheus-метрики
                                        │
                      PostgreSQL (Alembic-миграции) ◀── migrate (одноразовый контейнер)
                      Prometheus ──▶ Grafana (дашборд + 2 алерта, provisioned)
```

Это монолит из трёх слоёв. Главное решение: **расчёт сделан чистой функцией без БД и без часов**. Поэтому формулу можно проверить юнит-тестами, а повторяемость следует из построения.

## 2. Ключевые решения и компромиссы

| Решение | Почему | Цена / компромисс |
|---|---|---|
| Монолит FastAPI + Postgres | 2 дня и 1 человек. Проще деплоить, отлаживать и объяснять | Нет независимого масштабирования частей (MVP это не нужно) |
| Расчёт сделан чистой функцией | Тестируемость, воспроизводимость, нет скрытой зависимости от времени | Данные из БД сначала собираются в память. На сотнях карт это ~4 мс |
| Деньги в `Decimal`/`NUMERIC`, в JSON строкой | float даёт 0.1 + 0.2 ≠ 0.3, а JS теряет точность | Фронтенду строку нужно только отобразить, это не проблема |
| Округление **вниз до копейки**, один раз и после лимита | Советник не должен обещать больше, чем начислит банк. Одно место в коде (`money.round_down`) | Некоторые банки округляют до рубля. Мы чуть оптимистичнее таких банков (меньше 1 ₽) |
| Условия версионируются (`card_terms` с `valid_from/valid_to/checked_at`) | Нельзя выдавать устаревшее за актуальное. История сохраняется | Чуть сложнее схема |
| Базовый кэшбэк = правило категории `other` | Одна сущность, один путь в коде | — |
| Не выполнена `min_purchase` → откат на базовую ставку | Так ведут себя банки: покупка всё равно приносит базовый кэшбэк | Причина видна в `fallback_reason` |
| Лимит задаётся по паре «карта × категория» | Простая и понятная модель | Общий лимит на всю карту не моделируется (см. риски) |
| Тай-брейк: кэшбэк → остаток лимита → срок действия → `card.code` | Полностью детерминированный порядок | Автоинкрементный id **не используем**: он зависит от порядка импорта |
| `as_of` в запросе (по умолчанию «сегодня», МСК) | Воспроизводимость и тестируемость истечения условий | — |
| Пользователь = анонимный UUID в `X-User-Id` | Регистрация не нужна, и мы **не храним никаких реквизитов** | UUID можно «потерять», очистив браузер. Для MVP это допустимо |
| Использованный лимит хранится по месяцам (`period`) | Новый месяц начинается с полного лимита сам, без cron | — |
| Миграции выполняет отдельный контейнер `migrate` | Миграция упала, значит API не стартует. Нет гонок между репликами | Лишний шаг в compose |
| JSON-логи на stdlib → Loki, метрики `prometheus-client` | Минимум зависимостей в коде; логи и метрики в одной Grafana | Нет Sentry (платный или тяжёлый). Ошибки видны в Loki по request_id, в метрике `app_errors_total` и через алерт в Telegram |

## 3. Формула (что спросят первым)

```
правило  = правило категории (если есть и сумма ≥ min_purchase)
           иначе правило 'other' (если есть и сумма ≥ его min_purchase)
           иначе карта не подходит
raw      = сумма × ставка / 100
остаток  = max(лимит − уже_использовано_в_месяце, 0)        (если лимит есть)
кэшбэк   = round_down(min(raw, остаток), 0.01)
```
Пример из кейса (2 500 ₽, «Супермаркеты», демо-каталог):

| # | Карта | Расчёт | Кэшбэк |
|---|---|---|---|
| 1 | Банк Север «Продуктовая» | 7% = 175, упёрлись в лимит 150 | **150.00 ₽** |
| 2 | Река Банк «Двойка» | 5% = 125, лимита нет | **125.00 ₽** |
| 3 | Юг-Банк «Семейная» | 5% = 125, лимит 3000 | **125.00 ₽** |

Карты №2 и №3 набрали одинаково. «Двойка» выше, потому что у неё нет лимита и после покупки остаётся больше «запаса».
Горный Банк «Архивная» даёт 10%, но её условия истекли 30.09.2026. Поэтому она в `outdated` и в топ не попадает.

## 4. Граничные случаи (покрыты тестами)
- Для категории нет условия → базовая ставка (`no_category_rule`). Нет и её → карта не подходит.
- Сумма меньше `min_purchase` → базовая ставка (`below_min_purchase`). Сумма ровно на границе → ставка категории.
- Лимит уже исчерпан или «использовано» больше лимита → кэшбэк 0, отрицательных значений нет.
- `valid_to` включается в период. Только будущие условия → карта не подходит. Пересечение периодов версий запрещено при импорте.
- Округление: 333.33 × 1.5% = 4.99995 → **4.99**.
- Сумма: > 0, ≤ 10 000 000, не больше 2 знаков. Принимается и число, и строка.
- Перемешивание порядка карт на входе не меняет результат (20 случайных перестановок в тесте).
- `promo_url` не влияет на ранжирование (отдельный тест).
- Лишние поля в запросе (`pan`, `cvv`) отклоняются с 422: схемы запрещают неизвестные поля.
- БД недоступна → 503 `service_unavailable`, `/health` остаётся 200.

## 5. Наблюдаемость
- **Логи:** JSON в stdout → Alloy → **Loki** (7 дней) → поиск в Grafana по `request_id` (поле на дашборде или Explore). Каждая строка содержит `request_id`, который приходит из `X-Request-Id` или генерируется, возвращается клиенту в заголовке и в теле ошибки. Access-лог пишет метод, шаблон роута, статус и длительность.
- **Метрики:** `http_requests_total{method,route,status}`, `http_request_duration_seconds`, `recommendation_calc_seconds{scope}`, `recommendations_total{scope,category}`, `catalog_cards_total{status}`, `app_errors_total{code}`. В метках используется шаблон роута, а не URL, чтобы не раздувать кардинальность.
- **Grafana:** дашборд (метрики + логи) и алерты загружаются из файлов (provisioning), руками ничего не настраивается. Алерты: «доля 5xx > 5%» и «p95 > 500 мс», уведомления уходят в **Telegram** (токен в `.env.prod`, не в git).
- **Отслеживание ошибок:** стек и `request_id` пишутся в лог, растёт `app_errors_total{code="internal_error"}`, есть панель в Grafana и алерт.

## 6. Производительность (608 карт, MacBook, Postgres в Docker)
- Импорт 608 карт и 1 996 правил: ~6.6 с. Повторный импорт тоже ~6.6 с, без дублей.
- Чистый расчёт по 608 картам: p50 ≈ 4.4 мс, p95 ≈ 8 мс.
- Полный `POST /recommendations` (SQL + расчёт + сериализация 434 карт): p50 ≈ 65 мс, p95 ≈ 116 мс.
- Расчёт выполняется одним SQL-запросом: из БД берутся только правила нужной категории и `other`.

## 7. Риски релиза и как снижаем

| Риск | Как снижаем |
|---|---|
| Ломающая миграция | `downgrade` есть у каждой миграции. CI гоняет up → down → up и `alembic check`. Правило expand/contract. Перед релизом делаем `pg_dump` |
| Плохой релиз кода | Образ помечен git sha, откат = запуск предыдущего тега (docs/deploy.md). Healthcheck по `/ready` |
| Битый справочник | Весь файл валидируется до записи, импорт идёт одной транзакцией |
| Устаревшие условия | `valid_to` и `checked_at` в каждом ответе, истёкшие условия вынесены в `outdated` |
| Большой ответ на тысячах карт | Сейчас 434 карты дают 116 мс p95. Дальше можно пагинировать `eligible` или убрать его по флагу |
| Общий лимит карты не моделируется | Известное упрощение, расширяется таблицей лимитов уровня карты без смены API |
| Карта убрана из файла справочника | Импорт синхронизирует только карты из файла, остальные не трогает. Если у такой карты в БД остались «грязные» пересекающиеся версии (старые данные), фильтр каталога по категории может разойтись с показанной версией. Новые данные такими быть не могут: пересечения отсекает валидация файла |
| Демо-даты (условия до 30.06.2027) | Генератор детерминированный, даты легко сдвинуть |

## 8. Что нашло код-ревью и как исправили
Ревью кода всех этапов нашло 7 проблем. Все исправлены, и на каждую есть регрессионный тест.
- Переименование карты в справочнике роняло повторный импорт. Теперь идентичность карты — `code`.
- Удалённые из файла версии условий оставались в БД и могли пересекаться. Теперь версии карты синхронизируются с файлом.
- Любая ошибка БД выглядела как «БД недоступна» (503) и маскировала баги. Теперь 503 отдаётся только при ошибках соединения, остальное — 500 и алерт.
- Второй круг ревью: ошибки перегрузки Postgres (too many connections, statement timeout, исчерпан пул) снова дают 503 (классификация по SQLSTATE 08/53/57). Обмен названиями карт в одном файле больше не ломает импорт: уникальность проверяется отложенно (миграция 0002, `DEFERRABLE INITIALLY DEFERRED`). Обработчик OSError сужен до сетевых ошибок.
- Мелкие: фильтр каталога по категории смотрел не на ту версию условий, CLI падал с трейсбеком на битом CSV, `/ready` не учитывался в метрике ошибок, при остановке фоновая задача не дожидалась завершения.

## 9. 15 вероятных вопросов жюри

1. **Почему расчёт воспроизводим?** Это чистая функция от (карты, категория, сумма, дата, использование). Дата приходит параметром `as_of`, порядок полностью задан ключом сортировки, а последний тай-брейк сделан по стабильному строковому коду карты. Тест перемешивает вход 20 раз.
2. **Почему не float?** Двоичный float не представляет копейки точно. Везде `Decimal`, в БД `NUMERIC(12,2)`, в JSON строка.
3. **Почему округление вниз?** Это консервативно: мы не обещаем больше, чем даст банк. Правило одно, в `app/money.py`, применяется один раз после лимита.
4. **Что при равной выгоде?** Больше остаток лимита после покупки (без лимита лучше всех) → дольше действуют условия → код карты по алфавиту.
5. **Почему тай-брейк не по id?** Автоинкрементный id зависит от порядка импорта, а кейс требует независимости от порядка записей.
6. **Как не выдать устаревшие условия за актуальные?** У каждой версии есть период действия и дата проверки. Истёкшие идут в отдельный список `outdated` и никогда не попадают в топ. Даты есть в каждом элементе ответа.
7. **Как гарантируете, что реклама не влияет?** `promo_url` не входит в ключ сортировки, и это проверяет отдельный юнит-тест.
8. **Храните ли платёжные данные?** Нет. Пользователь — это анонимный UUID, а «моя карта» — ссылка на карту каталога. Схемы запрещают лишние поля, так что номер или CVV даже не принимаются.
9. **В чём нетривиальная фича?** Учёт использованного за месяц лимита по каждой «моей карте». Пример: «Продуктовая» после 140 ₽ использованного даёт 10 ₽ вместо 150 ₽ и уступает первое место. Месячная привязка сбрасывает лимит сама.
10. **Как работает идемпотентный импорт?** Upsert по ключам: банк по `code`, карта по `code` (публичный id, поэтому переименование не теряет «мои карты»), условия по (карта, версия). Версии и правила карты приводятся точно к файлу. Всё в одной транзакции, тест импортирует дважды и сверяет число строк.
11. **Что будет, если упадёт БД?** `/ready` вернёт 503, оркестратор уберёт инстанс из балансировки. API отвечает 503 вместо 500. `pool_pre_ping` переподключается после восстановления.
12. **Как откатить релиз?** Код откатывается запуском предыдущего образа по git sha. Схема откатывается через `alembic downgrade`: сначала откатываем код, потом схему, причём **новым образом**, потому что старый не знает об откатываемой миграции. Это мы нашли на репетиции отката. Миграции делаем обратно совместимыми.
13. **Как это тестируется?** 102 теста. Юнит-тесты проверяют формулу и валидацию, интеграционные работают с настоящим Postgres через миграции. CI идёт по цепочке: ruff → pyright → pytest → миграции → docker build.
14. **Выдержит ли сотни карт?** На 608 картах полный запрос держит p95 ≈ 116 мс, а сам расчёт занимает ≈ 4 мс. Расчёт делает один SQL-запрос с фильтром по категории.
15. **Почему монолит, а не микросервисы?** Одна предметная область, одна команда и 2 дня. Слои разделены, так что калькулятор можно вынести отдельно, если понадобится.
