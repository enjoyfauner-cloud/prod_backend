## Решения
- Монолит FastAPI, три слоя (api → services → db). Расчёт сделан чистой функцией без БД, отсюда тестируемость и воспроизводимость.
- Условия версионируются (`card_terms`: version, valid_from, valid_to, checked_at). Импорт запрещает пересечение периодов у одной карты.
- Базовый кэшбэк хранится как правило категории `other`.
- `min_purchase` для категории не выполнен → откат на `other` (с `fallback_reason`).
- Лимиты только по правилу (карта × категория). Общий лимит на карту не моделируем (упрощение MVP).
- Деньги: `Decimal` / `NUMERIC`, в JSON строкой. Округление **вниз до копейки** один раз, после лимита: не обещаем больше, чем даст банк.
- Тай-брейк: кэшбэк ↓ → остаток лимита после покупки ↓ (без лимита выше) → valid_to ↓ (бессрочно выше) → card.code ↑. Автоинкрементный id не используем, потому что он зависит от порядка импорта.
- Публичный id карты строковый slug (`cards.code`).
- `as_of` необязательный в запросе, по умолчанию «сегодня» в Europe/Moscow.
- Истёкшие условия → список `outdated`, никогда не попадают в top/eligible.
- Неподходящие карты → только `not_eligible_count`.
- Использованный лимит хранится по месяцам (`period` YYYY-MM) и учитывается только в `scope=my`.
- Пользователь = анонимный UUID в `X-User-Id`. Реквизитов нет.
- `promo_url` не участвует в ранжировании (будет тест).
- Максимальная сумма покупки 10 000 000 ₽.
- Папку `hello_world/` (шаблон IDE) не трогаем.
- Ошибки в едином формате `{"error": {code, message, details, request_id}}`.
