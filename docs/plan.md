# План backend «Советник — какую карту выбрать для покупки»

Этап 1: проектирование, кода пока нет. Контракт API для фронтенда лежит в [api-contract.md](api-contract.md).

## 1. Архитектура

Монолит на FastAPI с тремя слоями. Для MVP с одной командой и сроком два дня это самый простой вариант, который легко объяснить.

```
HTTP (FastAPI-роутеры, Pydantic-схемы, единый формат ошибок)
        │
Сервисы (бизнес-логика)
   ├─ calculator.py   — ЧИСТАЯ функция расчёта: без БД, без времени, без I/O
   ├─ ranking.py      — сортировка с тай-брейками
   ├─ recommendations.py — загрузить из БД → посчитать → ранжировать
   └─ catalog_import.py  — идемпотентный импорт справочника
        │
Данные (SQLAlchemy 2 async + PostgreSQL, миграции Alembic)
```

Расчёт сделан чистой функцией: на вход данные карт, сумма и дата, на выход результат. Поэтому формулу можно покрыть юнит-тестами без БД, а воспроизводимость следует из построения: одинаковый вход всегда даёт одинаковый выход.

## 2. Модель данных

```
banks           id PK, code UNIQUE, name
categories      code PK ('supermarkets', …, 'other'), name, sort_order
cards           id PK, code UNIQUE (публичный id, slug), bank_id FK, name,
                description, promo_url NULL, UNIQUE(bank_id, name)
card_terms      id PK, card_id FK, version INT, valid_from DATE, valid_to DATE NULL,
                checked_at DATE, source TEXT, UNIQUE(card_id, version)
cashback_rules  id PK, terms_id FK, category_code FK,
                rate_percent NUMERIC(5,2), monthly_limit NUMERIC(12,2) NULL,
                min_purchase NUMERIC(12,2) NULL, UNIQUE(terms_id, category_code)
user_cards      user_id UUID, card_id FK, added_at, PK(user_id, card_id)
card_usage      user_id UUID, card_id FK, category_code FK, period CHAR(7) 'YYYY-MM',
                used_cashback NUMERIC(12,2), updated_at,
                PK(user_id, card_id, category_code, period)
```

Почему так:
- **Условия версионируются** (`card_terms`). При смене условий банком появляется новая версия, старая остаётся. В любой момент можно показать, по каким условиям и на какую дату сделан расчёт.
- **Базовый кэшбэк хранится обычным правилом с категорией `other`** («Всё остальное»). Отдельная колонка не нужна, и логика «нет правила для категории → берём `other`» укладывается в одну строку.
- **`monthly_limit = NULL` означает «без лимита»**, а `min_purchase = NULL` означает «без минимальной суммы».
- **Публичный идентификатор карты строковый (`code`), например `"bank-sever-cashback-plus"`**. Автоинкрементный `id` зависит от порядка импорта, поэтому наружу и в тай-брейк он не попадает.
- **Использованный лимит хранится по месяцам** (`period`). С наступлением нового месяца остаток «сбрасывается» сам, фоновые задачи для этого не нужны.
- **Реквизитов карт в модели нет вообще.** У пользователя хранятся только анонимный UUID и ссылки на карты каталога.

## 3. Формула расчёта

Входные данные: категория `c`, сумма `A`, дата `as_of` (по умолчанию сегодня в часовом поясе `APP_TIMEZONE`, Europe/Moscow).

Для каждой карты:
1. **Выбор версии условий.** Берётся версия, у которой `valid_from ≤ as_of ≤ valid_to` (или `valid_to` пустая). Пересекающиеся периоды импорт не пропускает.
   - Если такой версии нет, но есть прошедшая, карта помечается `outdated`: она показывается отдельно и **никогда не попадает в топ**.
   - Если есть только будущие версии, карта в расчёт не попадает.
2. **Выбор правила.** Берётся правило категории `c`, если оно есть и `A ≥ min_purchase`. Иначе берётся правило `other`, если оно есть и `A ≥ его min_purchase`. Иначе карта **не подходит**. Причина отката на `other` попадает в разбор (`fallback_reason`): `no_category_rule` или `below_min_purchase`.
3. **Расчёт:**
   ```
   raw       = A × rate_percent / 100
   remaining = monthly_limit − used_this_month     (если лимит есть; не меньше 0)
   cashback  = min(raw, remaining)                 (если лимита нет: cashback = raw)
   cashback  = round_down(cashback, 0.01)
   ```
   `used_this_month` берётся из `card_usage` и учитывается только при `scope = "my"`. В остальных случаях он равен 0.

### Округление: вниз до копейки (`ROUND_DOWN`, шаг 0.01)
- Округление выполняется **один раз** в конце, после применения лимита, в одной функции `money.round_cashback()`.
- Почему вниз: советник не должен обещать больше, чем начислит банк. Округление вниз консервативно, и пользователь не разочаруется. Округление до копейки, а не до рубля, сохраняет различия между картами на маленьких суммах. Это компромисс, ниже он записан как риск.
- Деньги хранятся только в `Decimal`, в БД это `NUMERIC`. В JSON деньги передаются **строкой** (`"125.00"`), чтобы JS не превратил их во float.

### Ранжирование (детерминированное)
Ключи сортировки по порядку:
1. `cashback` по убыванию.
2. Остаток лимита после покупки по убыванию. Карта без лимита идёт выше: на ней останется больше «запаса» на следующие покупки.
3. `valid_to` по убыванию, пустая дата (бессрочно) выше: условия, которые дольше действуют, надёжнее.
4. `card.code` по возрастанию: стабильный строковый ключ, не зависящий от порядка в БД.

Поле `promo_url` («оформить карту») **не участвует** в расчёте и сортировке. На это есть отдельный тест.

## 4. Решения по неоднозначностям (они же записаны в NOTES.md)

| Вопрос | Решение | Почему |
|---|---|---|
| Как задаётся «базовый кэшбэк» | Правило с категорией `other` | Без отдельной сущности, один путь в коде |
| `min_purchase` для категории не выполнен | Откат на `other` | Так работают банки: покупка всё равно приносит базовый кэшбэк |
| Общий лимит на всю карту (по всем категориям) | Не моделируем, лимит задаётся по каждому правилу | Упрощение MVP, записано в рисках |
| Учитывать использованный лимит в `scope=catalog` | Нет, только в `scope=my` | Использование привязано к картам пользователя |
| Дата расчёта | Необязательный `as_of`, по умолчанию «сегодня» (МСК) | Воспроизводимость и тесты на истёкшие условия |
| Карта с нулевым кэшбэком (лимит исчерпан) | Подходит, но стоит в конце списка | Пользователь видит, почему она внизу |
| Максимальная сумма покупки | 10 000 000 ₽, 2 знака после запятой | Защита от мусора и переполнения |
| Неподходящие карты | Возвращается только их количество | При сотнях карт полный список не нужен |
| Папка `hello_world/` | Не трогаем | Это шаблон IDE, к проекту не относится |

## 5. Нетривиальная фича

**Расчёт с учётом использованного лимита.** Пользователь через `PUT /api/v1/me/cards/{card_id}/usage` указывает, сколько кэшбэка по категории уже получил в этом месяце. Рекомендация в `scope=my` считает остаток лимита. Например, карта с 10 % и лимитом 500 ₽, где 450 ₽ уже использовано, принесёт 50 ₽, а не 250 ₽, и может уступить карте с 5 % без лимита. Разбор показывает `limit_used_before` и `limit_remaining_before`.

## 6. Наблюдаемость (этап 6)
- JSON-логи (stdlib `logging` + свой форматтер), `request_id` из заголовка `X-Request-Id` или сгенерированный. Он возвращается в ответе и в теле ошибки.
- Метрики Prometheus: `http_requests_total{method,route,status}`, `http_request_duration_seconds{route}`, `recommendation_calc_seconds`, `catalog_cards_total{status}`.
- Grafana: provisioned-дашборд (RPS, p95, доля 5xx, время расчёта, размер каталога) и алерты «доля 5xx > 5 % за 5 мин» и «p95 > 500 мс за 5 мин».
